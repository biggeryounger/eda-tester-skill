# 测试计划 Agent 语义审查规范

版本：`2.0-draft`

状态：`CONFIGURED_DRAFT`

本文件只定义需要 Agent 理解命令说明、目标 EDA 工具和用例上下文后才能判断的语义规则。工作簿结构、字段格式、编号、换行、隐藏行和筛选范围等确定性要求由 `scripts/test_plan_validator.py` 检查，并作为该脚本的实现注释维护。

## Agent 语义审查

Agent 必须逐条记录 `PASS`、`FAIL` 或 `SPEC-GAP` 及理由。存在 `FAIL` 或未处理的 `SPEC-GAP` 时，不得确认用例设计，也不得宣称测试计划整体通过。

### PLAN-006：被测命令语义

- 判断“被测命令”是否为命令说明和目标工具中真实存在的主命令。
- 判断步骤中的辅助命令是否被错误填写为主命令。
- 工具版本或命令身份无法确认时记录 `SPEC-GAP`，不得猜测。

### PLAN-007：用例名称语义

- 判断场景名是否准确表达该用例的主要测试意图。
- 场景名不得使用没有区分度的泛化表述，例如仅写 `case`、`test` 或 `basic` 而无法辨认覆盖目标。

### PLAN-008：用例描述

- 描述必须真实说明测试场景、所覆盖的命令功能或 option，以及必要的设计状态。
- 多个测试点必须分别表达，且能与步骤、预期和覆盖项对应。
- 不得只复述命令名或使用“功能测试”等空泛描述。

### PLAN-009：用例步骤

- 判断准备、命令调用和结果收集步骤是否真实可执行，而不是只包含形式完整的文字。
- 涉及设计状态时，必须说明读入设计、流程阶段或前置对象。
- 涉及输出文件时，必须说明生成、清理和检查该文件的动作。
- 步骤必须与目标工具的命令顺序、依赖关系和初始化要求一致。

### PLAN-010：用例预期

- 每项预期必须包含结果概述、测试输入的构造数据说明，以及被测命令执行后对构造数据的影响。
- 构造数据应说明相关对象、属性、状态、连接、几何、文件或约束；不得只写“准备测试数据”或“加载 fixture”。
- 数据影响应明确新增、删除、修改、保留、拒绝写入或保持不变的内容。
- 正例必须给出可观察、可比较或可查询的结果，不能只写 `PASS` 或“执行成功”。
- 负例必须说明非法输入如何构造、预期错误类别或拒绝行为，以及拒绝后应保持不变的对象、文件或数据库状态。
- 多个预期必须与描述中的测试点和步骤逐项对应。

### PLAN-011：管理信息语义

- 填写责任人时，判断其是否为明确、可识别的责任主体。
- 未解决限制、工具差异和无法构造的场景必须写入备注，不能藏在预期结果中。
- 填写 Ticket 时，判断其编号或链接文本是否具有实际可追踪性。

### PLAN-012：正负属性一致

- `pos` 用例必须表达合法输入或受支持场景，预期为被工具接受并产生规定结果。
- `neg` 用例必须表达非法输入、缺失条件或拒绝场景，预期包含错误、warning、拒绝行为或状态不变性。
- 不得出现名称为 `pos` 但预期命令失败，或名称为 `neg` 但预期正常接受的语义冲突。

### PLAN-013：测试点语义追溯

- 根据版本化命令说明，确认每个必选参数、主要可选参数、枚举值和明确约束至少映射到一个真实有效的用例测试点。
- 映射必须在语义上实际覆盖目标，不得仅因描述或步骤中出现相同字符串就判定覆盖。
- 暂时无法覆盖的测试点必须写入备注并说明原因。
- Agent 必须报告已覆盖项、未覆盖项和无法确认的 `SPEC-GAP`。

## 审查输出

对每条用例至少输出：

- 用例 ID。
- PLAN 规则 ID。
- 状态：`PASS`、`FAIL` 或 `SPEC-GAP`。
- 判断理由和使用的命令说明或工具版本依据。
- 需要用户补充或修正的内容。

只有全部语义规则为 `PASS` 时，Agent 语义审查才通过。
