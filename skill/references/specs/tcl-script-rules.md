# TCL 用例 Agent 语义审查规范

版本：`4.0`

状态：`CONFIGURED`

本文件只规定必须由 Agent 结合被测命令说明、测试用例设计表和目标 EDA 工具语义完成的检查。目录、文件、命名、固定标记、白名单、调用形式和顺序等可确定性判定的规则，由 `scripts/tcl_convention_validator.py` 实现并在该脚本注释中维护，不在本文重复。

以下按“应该做”和“禁止做”分类；相同规则编号在两类中的要求共同构成该规则的审查依据。

## 应该做

### TCL-SEMANTIC-001：设计到脚本可追溯且测试动作一致

- 每个 Excel 有效用例行必须能唯一对应一个用例目录，脚本中的被测命令、选项组合、前置条件、正反属性和预期结果必须与该行一致。
- 多个 run 共同实现一个用例时，各步职责和最终断言必须能回溯到同一设计行。

### TCL-SEMANTIC-002：工具方言和设计初始化语义正确

- 命令、选项和初始化流程必须属于用户指定的 EDA 工具。
- `design.tcl` 提供的 top、网表、LEF、库、约束、DEF 等输入必须足以建立该测试需要的设计状态，且与被测场景相符。
- MMMC 的 mode、corner、library set、RC corner、delay corner、analysis view 等对象及关联关系必须支持当前场景和预期结果。
- 信息不足以判断初始化或 MMMC 是否正确时，记录 `SPEC-GAP`。


### TCL-SEMANTIC-003：用例检查点

- 每个用例必须至少包含一个 `pv_check_log`、`pv_check_qor` 或 `pv_check_golden` 检查点，用于验证该用例的预期结果。

### TCL-SEMANTIC-004：多步数据流和交付范围完整

- 多步 run 的执行顺序、依赖关系、前一步产物和后一步消费必须在语义上连贯。
- 每个测试用例设计行都必须完成脚本映射；所有必需初始化、被测动作、检查点、golden 或报告依赖均应随交付提供或有明确可用来源。
- 用例应能在声明的运行入口下独立执行。
- 存在遗漏、冲突或无法确认的外部依赖时，分别记录 `FAIL` 或 `SPEC-GAP`。


## 禁止做

- **TCL-SEMANTIC-001**：不得遗漏设计步骤、增加未经确认的测试目标，或把负向用例改写为仅验证命令可执行的正向用例。
- **TCL-SEMANTIC-002**：不得混用 Optimus 与 iTools / Innovus 方言；不得依赖未声明的预加载会话状态；不得仅满足文件结构而忽略 MMMC 对象及关联关系的场景语义；信息不足时不得猜测为 `PASS`。
- **TCL-SEMANTIC-003**：不得只以命令被调用或日志存在证明预期结果；`pv_check_log` 的命令块、`-filter` 和 `-match` 不得屏蔽关键失败；不得仅靠结构检查判定断言充分性。
- **TCL-SEMANTIC-004**：不得引用未生成或错误场景的中间产物；不得把关键语义依赖隐藏在用户机器、交互会话或未交付文件中。
- **审查与交付**：不得由确定性脚本检查的 `PASS` 替代 Agent 语义审查；不得在任何 `FAIL` 或未解决的 `SPEC-GAP` 存在时交付。
