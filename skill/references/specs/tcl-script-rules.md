# TCL 用例 Agent 语义审查规范

版本：`4.0`

状态：`CONFIGURED`

本文件只规定必须由 Agent 结合被测命令说明、测试用例设计表和目标 EDA 工具语义完成的检查。目录、文件、命名、固定标记、白名单、调用形式和顺序等可确定性判定的规则，由 `scripts/tcl_convention_validator.py` 实现并在该脚本注释中维护，不在本文重复。

## Agent 语义审查

### TCL-SEMANTIC-001：设计到脚本可追溯且测试动作一致

- 每个 Excel 有效用例行必须能唯一对应一个用例目录，脚本中的被测命令、选项组合、前置条件、正反属性和预期结果必须与该行一致。
- 脚本不得遗漏设计步骤、增加未经确认的测试目标，或把负向用例改写为仅验证命令可执行的正向用例。
- 多个 run 共同实现一个用例时，各步职责和最终断言必须能回溯到同一设计行。

### TCL-SEMANTIC-002：工具方言和设计初始化语义正确

- 命令、选项和初始化流程必须属于用户指定的 EDA 工具及版本；不得混用 Optimus 与 iTools / Innovus 方言。
- `design.tcl` 提供的 top、网表、LEF、库、约束、DEF 等输入必须足以建立该测试需要的设计状态，且与被测场景相符；不得依赖未声明的预加载会话状态。
- MMMC 的 mode、corner、library set、RC corner、delay corner、analysis view 等对象及关联关系必须支持当前场景和预期结果，不得仅满足文件结构。
- 信息不足以判断初始化或 MMMC 是否正确时，记录 `SPEC-GAP`，不得猜测为 PASS。

### TCL-SEMANTIC-003：检查点能够证明预期结果

- 检查点必须观察被测命令应产生的行为或状态变化，而不是只证明命令被调用或日志存在。
- `pv_check_log` 的命令块、`-filter` 和 `-match` 不得屏蔽关键失败；`pv_check_golden` 的比较对象必须稳定且适合该场景；QoR 指标和容差必须有业务意义。
- 正向用例应证明预期结果成立；负向用例应证明非法输入被拒绝、错误被识别，且必要时确认设计状态未被错误修改。
- 仅靠结构检查无法判断断言充分性；缺少可执行判据时记录 `SPEC-GAP`。

### TCL-SEMANTIC-004：多步数据流和交付范围完整

- 多步 run 的执行顺序、依赖关系、前一步产物和后一步消费必须在语义上连贯，不得引用未生成、错误场景或不兼容版本的中间产物。
- 每个测试用例设计行都必须完成脚本映射；所有必需初始化、被测动作、检查点、golden 或报告依赖均应随交付提供或有明确可用来源。
- 用例应能在声明的运行入口下独立执行；不得把关键语义依赖隐藏在用户机器、交互会话或未交付文件中。
- 存在遗漏、冲突或无法确认的外部依赖时，分别记录 `FAIL` 或 `SPEC-GAP`。

## 审查记录与通过条件

- 对每条适用规则记录 `PASS`、`FAIL` 或 `SPEC-GAP`，并附用例 ID、文件位置和判断依据。
- `FAIL` 表示脚本与已知需求或工具语义不一致；`SPEC-GAP` 表示现有材料不足以完成语义判断，需要用户补充或确认。
- 只有所有适用规则均为 `PASS` 时，Agent 语义审查才通过。任何 `FAIL` 或未解决的 `SPEC-GAP` 都必须停止交付并进入等待，不得由确定性脚本检查的 PASS 替代。
