# 测试场景生成策略

版本：`1.2`

测试设计开始前必须由用户选择策略，允许多选。不同策略生成的场景取并集；重复场景合并，并保留全部策略标签。

## 单用例多测试点

默认目标不是“一项 option 一个用例”，而是在保证语义正确和结果可诊断的前提下，让一个用例覆盖尽可能多的被测命令选项与测试点。

优先合并的条件：

- 属于同一被测命令和同一正负属性。
- 前置设计状态一致，不需要重复加载或切换互斥的流程阶段。
- option 可以在同一次命令调用中合法组合，或可以在同一脚本内按顺序完成相关调用。
- 检查点类型兼容，预期结果可以分别观察并清楚归因。

必须拆分的条件：

- 选项互斥或组合非法，除非该组合本身就是目标负向测试点。
- 前置设计状态不同，合并会改变被测语义。
- 预期结果的性质不同，例如正常接受与明确拒绝不得放入同一用例。
- 合并多个独立非法输入会损害故障定位，无法确认具体是哪一个测试点触发错误。
- 某个枚举值或边界值需要独立运行才能观察结果。

每个合并用例必须在 Excel 中逐项对应：

- 用例描述列写成 `测试点 1`、`测试点 2`……，列出覆盖的 option、枚举或约束。
- 用例步骤列写成 `步骤 1`、`步骤 2`……，说明每个测试点如何被执行。
- 用例预期列写成 `预期 1`、`预期 2`……，与测试点和步骤保持可追溯对应。
- 覆盖矩阵仍按单个 option/枚举/约束记录，不能因为合并用例而漏记测试点。

## 策略选择交互

向用户提出以下问题，并等待回答后再生成测试设计：

```text
请选择本次测试策略（可多选）：
1. Smoke case：覆盖被测命令的所有选项与枚举值
2. 正向覆盖：从业务场景出发设计合法、可成功执行的用例
3. 负向覆盖：从边界值、异常值和选项冲突出发设计预期拒绝或报错的用例
```

- 用户未选择时不得默认替用户决定，也不得提前生成测试计划或 TCL 用例。
- 用户已在当前请求中明确选定策略时，复述选择并直接继续，不重复询问。
- 选择多项时按 `Smoke case`、`正向覆盖`、`负向覆盖` 的顺序组织场景。
- 测试设计必须记录本次选中的策略；Excel 中每个场景的“用例描述”以 `[strategy:smoke]`、`[strategy:positive]`、`[strategy:negative]` 或多标签组合开头，标记其来源策略。

## 用例设计确认门禁

完成场景分解和覆盖矩阵后，先生成并通过 Layer 1 验证 Excel 测试计划，将该 Excel 与完整用例设计摘要交给用户审阅；确认前不得生成 TCL。每个拟生成用例至少展示：

- 用例 ID 和策略标签。
- 逐项测试点及覆盖的 option、枚举、边界或约束。
- EDA 设计初始化前置和必需输入。
- 编号步骤及逐项对应的预期结果。
- 已覆盖需求、未覆盖项、信息缺口和假设。

展示后明确询问：`确认用例设计可用于生成 TCL 吗？`，并等待用户回答。

- 只有用户明确表示“确认”“可用”“按此生成”或等价批准时，才能生成 TCL。
- 选择测试策略不等于确认用例设计；用户最初要求“生成测试”也不等于批准尚未展示的设计。
- 用户提出修改时，先修改用例设计和覆盖矩阵，重新生成并验证 Excel，再完整展示并重新确认。
- 用户未回复、回复含糊或仅补充资料时，保持在设计确认阶段，不生成用例脚本。

## 1. Smoke case

目标：用精简的合法用例快速确认命令接口可用，并覆盖所有选项与枚举值。

覆盖要求：

- 包含一个只使用必选参数的最小合法场景；没有必选参数时使用命令默认调用。
- 每个可选选项至少在一个合法场景中出现一次。
- 每个枚举型选项的每个受支持枚举值至少出现一次。
- 布尔开关覆盖显式启用；如果语法同时支持显式关闭值，也覆盖关闭值。
- 有依赖关系的选项使用满足依赖的最小组合，不为追求单选项隔离而生成必然失败的 smoke 用例。
- 在不损失选项和枚举覆盖的前提下，必须优先合并兼容选项，使每个用例覆盖更多测试点并控制用例数量。
- Smoke case 只生成正向用例，不包含缺参、非法值、边界外值或冲突组合。

完成条件：建立“选项/枚举值 → 用例”映射，所有已知选项和枚举值均至少映射一次；无法合法执行的项记录为缺口，不伪造覆盖。

## 2. 正向覆盖

目标：从真实业务流程和设计状态出发，验证命令在受支持场景中的行为与结果。

覆盖要求：

- 按用户目标、设计阶段、对象类型、数据规模和上下游流程识别业务场景。
- 覆盖最小合法流程、常用流程、关键状态转换及文档明确支持的组合用法。
- 为每个场景写清前置设计状态、业务动作、被测命令和可观察的后置结果。
- 优先断言对象变化、报告内容、输出文件或 QoR 指标，不得只以退出码或“执行成功”作为预期。
- 只生成预期被工具接受的 `posNNN_<scenario>` 用例。
- 不要求机械覆盖每个选项；若同时选择 Smoke case，则由 Smoke case 补足选项和枚举覆盖。
- 同一业务流程中的兼容 option 和多个可观察后置条件优先放入一个用例。

完成条件：每个识别出的核心业务场景至少对应一个正向用例；未覆盖场景及原因写入测试设计备注。

## 3. 负向覆盖

目标：验证命令对非法输入、边界外输入、异常状态和冲突组合的拒绝与诊断行为。

覆盖要求：

- 边界值：覆盖最小值、最大值以及边界外的相邻值；无明确数值范围时不得臆造边界。
- 异常值：覆盖错误类型、非法枚举、空值、格式错误、不存在对象以及不允许的特殊字符；只选择命令语义适用的类别。
- 必选项：每个必选参数至少有一个缺失场景。
- 选项冲突：覆盖文档声明的互斥、依赖缺失、非法组合及不允许的重复选项。
- 状态异常：覆盖错误流程阶段、缺失前置数据、对象状态不满足和环境依赖缺失；许可证或基础设施故障必须与命令行为失败区分。
- 每个场景说明预期错误类别、warning、拒绝行为或状态不变性，不强依赖未经文档保证的完整错误文本。
- 一个负向用例通常只保留一个主要非法因素，以维持故障定位；可以同时携带满足前置依赖所需的合法 option。
- 只生成预期被工具拒绝或明确告警的 `negNNN_<scenario>` 用例。

完成条件：所有文档明确给出的范围、枚举限制、互斥和依赖约束均有反例；不能安全构造的负向场景记录原因。

## 多策略合并规则

- 同一输入、前置状态、动作和预期相同的场景只保留一条；前置状态和预期性质兼容时进一步合并不同测试点。
- Smoke case 与正向覆盖重复时保留一条正向用例，同时标记 `smoke`、`positive`。
- 正向与负向场景不得合并。
- 用例编号在合并去重后生成；正例和反例分别从 `001` 连续编号。
- 最终测试设计按所选策略分别报告覆盖摘要、未覆盖项和假设。
