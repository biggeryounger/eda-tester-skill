# EDA 用例生成知识库设计

版本：`1.0-draft`

## 1. 建设目标

建立一套面向 **Optimus**、**iTools / Innovus**、**PrimeTime** 的系统化用例生成知识库，为测试场景设计、Excel 测试计划生成和 TCL 用例生成提供可检索、可适配、可追溯、可验证的知识。

知识库解决以下问题：

- 复用经过验证的测试思想、业务场景、初始化方式和检查点。
- 从历史缺陷、命令约束和真实案例中补充命令手册未显式覆盖的测试点。
- 根据工具、版本、设计阶段和环境条件筛选适用知识，避免错误复用。
- 为生成结果保留“需求 → 知识 → 场景 → Excel → TCL → 验证结果”的完整证据链。
- 将经验知识与确定性规则分离，知识库辅助生成，但不替代静态检查和实机验证。

## 2. 设计原则

1. **结构化优先**：核心事实使用版本化结构数据保存，正文和 TCL 只作为关联资产。
2. **来源可追溯**：每条知识必须记录来源、采集时间、适用范围和责任状态。
3. **版本严格隔离**：工具和版本不匹配的知识只能作为候选，不能自动提升为当前事实。
4. **事实与经验分离**：文档事实、实机观察、设计建议、未知项分别建模。
5. **脱敏后入库**：不得保存许可证、PDK、设计数据库、内部绝对路径、运行日志原文或用户身份信息。
6. **验证状态显式化**：静态检查通过不等于实机运行通过，二者分别记录。
7. **生成与验证解耦**：知识检索可以参与生成，最终交付仍必须通过现有 Layer 1、Layer 2A、Layer 2B 门禁。
8. **可演进**：所有数据结构、规则和知识条目都有版本；变更不得静默覆盖历史事实。

## 3. 系统边界

### 3.1 知识库负责

- 存储命令语义、测试模式、业务场景、故障模式、环境前置、检查点和历史案例。
- 接收当前测试目标，检索并排序候选知识。
- 对候选知识执行工具、版本、设计阶段、前置条件和可信度过滤。
- 输出带来源和适用性说明的候选测试点、场景骨架及检查建议。
- 记录知识在某次生成中的使用情况和后续验证结果。

### 3.2 知识库不负责

- 不代替原始命令手册或用户明确提供的需求。
- 不推断文档没有给出的枚举、边界、默认值或错误文本。
- 不直接决定用户的 Smoke case、正向覆盖或负向覆盖策略。
- 不绕过用例设计确认门禁自动生成 TCL。
- 不把 Nagelfar 静态通过解释为目标 EDA 工具实机通过。
- 不保存或分发目标项目的敏感设计资产。

## 4. 总体构成

知识库由六层组成：

```text
来源层
  命令手册 / -help / 用户需求 / 历史用例 / 缺陷 / 实机结果
                         ↓
采集与治理层
  解析、脱敏、去重、版本标记、来源登记、质量检查
                         ↓
知识模型层
  命令知识、场景模式、故障模式、环境前置、检查点、案例资产
                         ↓
存储与索引层
  结构化主库 + 文档/脚本资产库 + 全文/语义辅助索引
                         ↓
检索与适配层
  过滤、召回、排序、冲突处理、覆盖补全、场景合并拆分
                         ↓
生成与反馈层
  覆盖矩阵、Excel、TCL、静态门禁、实机结果、知识回写
```

## 5. 知识分类

### 5.1 命令语义知识 `command_spec`

描述命令本身可确认的事实：

- 工具、命令名和适用版本范围。
- Syntax、必选参数、可选参数、参数数量和类型。
- 默认值、枚举值、数值范围和可重复性。
- 互斥、依赖、至少一个、顺序等关系。
- 适用设计阶段和对象类型。
- 文档明确给出的消息、输出和副作用。
- 未解决的 `SPEC-GAP`。

该类知识优先来自用户手册、工具 `-help` 和已验证结构化命令数据。

### 5.2 测试模式知识 `test_pattern`

描述可跨命令复用的测试设计方法，例如：

- 最小合法调用。
- 所有 option 和枚举覆盖。
- 必选项缺失、非法枚举、边界内外值。
- 互斥项组合、依赖项缺失、重复参数。
- 错误设计阶段、对象不存在、空集合和大规模对象集。
- 写文件命令的旧文件清理、生成、非空和 golden 比较。
- 多步状态传递和结果可观察性。

测试模式只描述抽象方法，不绑定用户设计路径或具体 PDK 值。

### 5.3 业务场景知识 `scenario_pattern`

描述工具流程中的典型使用场景：

- setup、floorplan、place、CTS、route、post-route 等阶段。
- 输入对象、设计状态、上游动作和下游观察点。
- 合法操作序列和状态转换。
- 场景适用的正负属性以及拆分、合并条件。

### 5.4 故障模式知识 `failure_pattern`

来源于历史缺陷、失败用例和常见误用：

- 触发条件与最小复现条件。
- 预期错误类别、warning、状态不变性或异常输出。
- 易混淆的基础设施故障与命令行为故障。
- 已修复版本、受影响版本和回归优先级。
- 对应的最小检查点和故障定位建议。

### 5.5 环境与初始化知识 `environment_recipe`

描述用例运行所需但不属于命令语法的前置条件：

- 工具和可选版本。
- 设计激活命令及执行顺序。
- design、library、LEF、netlist、DEF、MMMC、constraint 等输入类别。
- 适用的设计阶段和对象准备条件。
- 允许的系统环境变量及路径策略。

该类知识只保存变量角色和可移植结构。具体目标设计值继续由 `assets/design-profiles.json` 管理，不复制到知识库。

### 5.6 检查点知识 `checkpoint_pattern`

描述如何观察测试结果：

- `pv_check_log`：适用消息类别、`-filter` 和 `-match` 选择原则。
- `pv_check_golden`：实际文件生成、旧文件清理、golden 位置和比较时机。
- `pv_check_qor`：适用指标、前置阶段和容差来源。
- 对象数量、属性变化、文件存在性和状态不变性的观察方法。

知识库不得保存伪造的工具输出或没有来源保证的完整报错文本。

### 5.7 历史案例知识 `case_record`

保存一个已经设计或执行过的具体案例的结构化摘要：

- 用例 ID、命令、策略标签、正负属性和测试点。
- 前置状态、步骤、预期和覆盖项。
- 引用的命令知识、测试模式、故障模式和检查点。
- Excel 与 TCL 资产的内容摘要及校验和。
- Layer 1、Layer 2A、Layer 2B 和实机运行结果。
- 适用范围、已知限制和脱敏状态。

具体案例不得直接复制到新交付物；必须先经过当前上下文适配。

## 6. 核心数据模型

所有知识条目使用统一信封结构：

```json
{
  "schema_version": "1.0",
  "knowledge_id": "KB-CMD-000001",
  "knowledge_type": "command_spec",
  "title": "Optimus check_design_data command semantics",
  "tool": "Optimus",
  "command": "check_design_data",
  "version_scope": {
    "kind": "exact",
    "values": ["21.1"]
  },
  "design_stages": ["setup"],
  "polarity": "both",
  "strategies": ["smoke", "positive", "negative"],
  "facts": {},
  "prerequisites": [],
  "expected_observations": [],
  "source_refs": ["SRC-000001"],
  "validation": {
    "content_status": "reviewed",
    "static_status": "passing",
    "runtime_status": "not_run",
    "last_verified": "2026-08-23"
  },
  "confidence": "high",
  "sensitivity": "sanitized",
  "tags": [],
  "supersedes": [],
  "created_at": "2026-08-23T00:00:00+08:00",
  "updated_at": "2026-08-23T00:00:00+08:00"
}
```

### 6.1 必需字段

| 字段 | 作用 |
|---|---|
| `knowledge_id` | 稳定且不可复用的知识编号 |
| `knowledge_type` | 知识分类 |
| `tool`、`command` | 适用工具和命令；跨命令模式可使用受控通配标记 |
| `version_scope` | 精确版本、版本范围、版本无关或未知 |
| `facts` | 类型专属的结构化正文 |
| `source_refs` | 一个或多个来源记录 |
| `validation` | 内容、静态检查和实机运行的独立状态 |
| `confidence` | `high`、`medium`、`low`，由确定性规则计算或人工审核确认 |
| `sensitivity` | `public`、`internal_sanitized`、`restricted`、`rejected` |

### 6.2 来源模型 `source_record`

每个来源至少记录：

- 来源 ID、类型、标题和内容摘要校验和。
- 工具、版本、发布日期或采集时间。
- 原始位置或受控资产引用。
- 采集方式、脱敏状态和授权范围。
- 来源优先级和是否可作为事实依据。

建议的来源优先级：

1. 当前目标版本的官方手册或工具 `-help`。
2. 用户明确提供并确认的当前版本材料。
3. 当前版本实机通过案例。
4. 其他版本官方材料。
5. 脱敏历史案例和工程经验。
6. 未验证建议，只能生成候选或缺口。

## 7. 存储设计

建议采用“结构化主库 + 资产库 + 派生索引”的组合，而不是只使用向量数据库。

### 7.1 结构化主库

初期使用版本化 JSON，规模增大后迁移到 SQLite 或关系数据库。主库保存：

- 知识条目和来源元数据。
- 工具、命令、版本和设计阶段索引。
- 知识之间的引用、派生、冲突和替代关系。
- 验证状态、审核记录和使用记录。

结构化主库是事实和追溯关系的唯一正式来源。

### 7.2 资产库

保存允许复用的脱敏材料：

- 命令说明和解析后的结构数据。
- 场景摘要、Excel 行数据和 TCL 片段模板。
- 静态验证报告和允许保留的实机结果摘要。

每个资产由内容校验和寻址，禁止以机器绝对路径建立引用。

### 7.3 派生索引

- 精确索引：tool、command、version、stage、strategy、polarity、validation status。
- 全文索引：标题、摘要、测试点、错误类别和标签。
- 语义索引：只用于召回相似内容，不作为事实判定或最终排序的唯一依据。

索引可以重建，不得成为主数据来源。

## 8. 知识关系

核心关系包括：

- `derived_from`：知识由某个来源或知识条目派生。
- `applies_to`：模式适用于某工具、命令、版本或阶段。
- `requires`：场景需要环境、对象或其他知识前置。
- `covers`：案例覆盖某 option、枚举、约束、需求或缺陷。
- `uses_checkpoint`：场景使用某检查点模式。
- `conflicts_with`：两个事实或模式不可同时采用。
- `supersedes`：新条目替代旧条目，但保留历史记录。
- `validated_by`：知识由静态门禁或实机结果验证。
- `instantiated_as`：抽象模式被实例化为具体案例。

## 9. 检索与适配流程

### 9.1 查询上下文

每次查询至少输入：

- 工具、命令和已知版本。
- 用户选择的测试策略。
- 当前命令结构化语义和 `SPEC-GAP`。
- 目标设计阶段、对象类型和设计初始化条件。
- 正负属性、期望覆盖范围和可用检查点。

### 9.2 处理步骤

1. **硬过滤**：按工具、命令、版本兼容性、敏感级别和禁用状态筛选。
2. **精确召回**：检索同命令、同版本和同阶段的命令知识及案例。
3. **模式召回**：检索适用的测试模式、故障模式和检查点。
4. **相似召回**：在同一工具或命令族内检索相似历史场景。
5. **冲突检测**：比较当前手册、用户材料和知识库事实；出现冲突时按来源优先级处理并记录缺口。
6. **适配**：替换命令、option 和抽象对象角色；设计路径只能从当前 design profile 注入。
7. **覆盖补全**：依据所选策略检查 option、枚举、约束、业务场景和负向类别是否遗漏。
8. **合并拆分**：遵循当前“单用例多测试点”规则，兼容项合并，不同预期性质或互斥前置拆分。
9. **候选输出**：输出带知识 ID、来源、适用性、假设和缺口的场景候选。

### 9.3 排序建议

排序分数由可解释字段组成：

```text
适用性 = 工具匹配 + 命令匹配 + 版本匹配 + 阶段匹配
可信度 = 来源等级 + 内容审核 + 静态验证 + 实机验证
价值度 = 覆盖增量 + 历史缺陷关联 + 检查点可观察性
风险项 = 版本未知 + 来源冲突 + 前置缺失 + 低可信度
```

排序公式和权重必须版本化；低可信度知识不得因为语义相似度高而超过当前版本官方事实。

## 10. 生成流程集成

知识库插入现有工作流的位置如下：

```text
命令资料解析
    ↓
形成当前命令事实和缺口
    ↓
用户选择测试策略
    ↓
查询知识库并生成候选测试点
    ↓
版本/环境适配、冲突处理、覆盖矩阵
    ↓
生成并验证 Excel
    ↓
展示知识来源、假设和缺口，等待用户确认
    ↓
生成 TCL 目录树
    ↓
Layer 1 → Layer 2A → Layer 2B
    ↓
可选实机执行及结果回写
```

每个生成场景应在内部工作数据中保留：

- 使用的知识 ID。
- 对应的来源 ID。
- 适配前后的差异。
- 被拒绝候选及拒绝原因。
- 当前仍未解决的缺口。

这些追溯数据默认作为内部产物，不强制写入用户 Excel；需要审计时可生成独立报告。

## 11. 可信度与生命周期

### 11.1 内容状态

- `draft`：已采集，尚未完成结构与来源检查。
- `reviewed`：结构、来源、脱敏和适用范围已审核。
- `approved`：允许参与正式生成。
- `deprecated`：仍可追溯，但默认不召回。
- `rejected`：内容错误、敏感或不可验证，不得使用。

### 11.2 验证状态

分别记录：

- `content_status`：内容治理状态。
- `static_status`：`not_run`、`passing`、`failing`、`tool_unavailable`。
- `runtime_status`：`not_run`、`passing`、`failing`、`environment_blocked`。

不得使用一个笼统的“已验证”字段合并三种状态。

### 11.3 更新策略

- 事实发生变化时创建新版本，并通过 `supersedes` 关联旧版本。
- 新工具版本发布后，旧版本知识不自动继承到新版本。
- 长期未复核或来源失效的知识降低可信度并进入待审核队列。
- 实机失败优先形成失败观察记录；只有确认知识本身错误后才修改或废弃知识。

## 12. 知识入库流程

```text
提交来源
  → 内容校验和与重复检测
  → 自动脱敏扫描
  → 结构化解析
  → Schema 校验
  → 工具/版本/命令一致性检查
  → 人工审核事实边界
  → 静态验证（适用时）
  → 发布为 approved
```

每类新规则或验证规则必须具有通过和失败样例。入库失败应返回稳定的诊断 ID，不产生半成品正式条目。

## 13. 脱敏与安全

禁止入库：

- EDA 许可证内容和许可证服务器地址。
- PDK、library、设计数据库和完整运行日志。
- 用户目录、内网路径、主机名、账号和组织信息。
- 未授权的手册全文或其他受限资料。
- 可直接映射到客户设计的 top、cell、net、clock 和具体调优值。

允许保存：

- 抽象变量角色，如 `<TOP>`、`<LEF_LIST>`、`<DEF_FILE>`。
- 脱敏后的最小 TCL 结构和检查点模式。
- 来源摘要、内容校验和以及受控位置引用。
- 不包含客户数据的验证状态和诊断类别。

发布前执行确定性扫描；发现敏感模式时将条目标记为 `rejected`，不得只依靠人工或 Agent 判断。

## 14. 确定性验证要求

知识库至少需要以下自动检查：

| 规则组 | 检查内容 |
|---|---|
| `KB-SCHEMA` | Schema 版本、必需字段、枚举和数据类型 |
| `KB-ID` | ID 唯一性、引用存在性、禁止循环替代关系 |
| `KB-SOURCE` | 来源完整性、内容校验和和授权状态 |
| `KB-SCOPE` | 工具、命令、版本和设计阶段的合法组合 |
| `KB-FACT` | option/关系引用一致性，未知事实必须显式标记 |
| `KB-SECURITY` | 敏感路径、许可证、客户标识和禁止资产检测 |
| `KB-VALIDATION` | 内容、静态和实机状态不得互相冒充 |
| `KB-RETRIEVAL` | 固定查询的召回、过滤、排序和冲突处理结果 |
| `KB-TRACE` | 生成场景能够追溯到知识和来源 |

所有规则均应有稳定规则 ID、通过样例和失败样例。验证失败返回非零退出码。

## 15. 质量指标

建议跟踪：

- 命令覆盖率：已有知识的命令数 / 目标命令数。
- 版本覆盖率：具有精确版本知识的命令比例。
- 测试点复用率：生成场景中引用知识库的测试点比例。
- 覆盖增量：使用知识库后新增且有效的需求或故障模式覆盖数。
- 冲突率：检索知识与当前来源冲突的比例。
- 误用率：因版本、阶段或环境不匹配被验证拒绝的复用比例。
- 实机通过率：知识辅助生成用例的实机通过比例。
- 追溯完整率：具有完整知识和来源链的生成场景比例。
- 脱敏拒绝率：因敏感信息被阻断的入库比例。

质量指标用于改进知识，不作为绕过单条交付门禁的依据。

## 17. 分阶段落地

### 阶段 1：最小可用知识库

- 定义 JSON Schema、知识 ID 和来源模型。
- 首先支持 `command_spec`、`test_pattern`、`checkpoint_pattern` 和 `case_record`。
- 使用 JSON 主库和精确字段检索。
- 实现 Schema、引用、版本、脱敏和追溯检查。
- 选取 2～3 个 Optimus 或 iTools / Innovus 命令建立黄金样例。

### 阶段 2：生成流程接入

- 在场景设计前加入知识检索。
- 输出候选来源、适配差异、冲突和拒绝原因。
- 将知识 ID 写入内部场景 JSON 和覆盖矩阵。
- 建立固定查询回归集，验证召回与排序稳定性。

### 阶段 3：案例反馈闭环

- 回写 Layer 1、Layer 2A、Layer 2B 和实机结果。
- 从已确认案例生成待审核知识，不自动发布。
- 增加故障模式、环境配方和跨命令场景模式。

### 阶段 4：规模化检索

- 主库迁移到 SQLite 或服务化数据库。
- 增加全文和语义辅助召回。
- 建立权限、审核、版本迁移、质量仪表盘和过期复核机制。

## 18. 验收标准

知识库首个可用版本应满足：

1. 任一生成测试点都能追溯到当前需求、知识条目和来源，或明确标记为本次新设计。
2. 工具或版本不匹配的案例不会被自动当作当前事实复用。
3. 文档事实、工程经验、静态验证和实机验证状态明确分离。
4. 缺少来源、存在未知引用或包含敏感信息的条目无法发布。
5. 固定查询集的召回、过滤、冲突处理和排序结果可确定性复现。
6. 知识库关闭或无匹配结果时，现有测试生成流程仍可按命令资料继续工作。
7. 知识库生成的候选场景仍需通过 Excel 确认门禁和 Layer 1、Layer 2A、Layer 2B。
8. 每条知识验证规则具有通过和失败测试样例。

## 19. 与当前项目的关系

该知识库是 EDA Tester Skill 的上游辅助系统。当前项目中的：

- `references/command-spec-format.md` 提供命令语义输入格式。
- `references/test-strategies.md` 决定候选场景如何覆盖、合并和拆分。
- `assets/design-profiles.json` 继续作为目标设计路径和值的唯一来源。
- `scripts/generate_test_plan.py` 继续负责生成并验证 Excel。
- `scripts/validate.py delivery` 继续作为最终统一交付门禁。

因此，知识库提高测试设计的完整性和复用能力，但不改变现有交付物格式，也不削弱用户确认和确定性验证要求。
