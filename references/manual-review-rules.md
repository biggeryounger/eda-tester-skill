# EDA 用例人工语义审查

静态检查器不能证明业务语义正确。生成器必须在写 Excel 前和交付门禁后各执行一次下列审查；任一答案为“否”或“未知”时，记录到备注/缺口并停止 TCL 交付。

1. 工具、命令及已知版本是否准确，是否只指定一个主被测命令？
2. 用户是否明确选择了 Smoke、正向覆盖、负向覆盖；最终场景是否为所选策略并集？
3. 必选参数、主要可选参数、枚举、边界、互斥、依赖、环境前置和版本差异是否逐项映射到用例或明确缺口？
4. 合并是否只发生在同设计状态、同正负属性、兼容 option、同类预期之间；互斥状态、不同预期及影响故障定位的非法因素是否拆分？
5. `pos` 是否全为合法接受场景，`neg` 是否全为非法、缺失条件、拒绝或告警场景？
6. 每条描述是否包含场景、功能/option 和必要设计状态；步骤是否写清准备、加载、被测动作和结果收集？
7. 每条预期是否说明构造对象及可查询的变化/不变性；负例是否同时说明非法构造、拒绝类型及拒绝后不变状态？
8. MMMC 的 setup/hold、PVT、RC 映射和对象引用是否来自原用例、目标版本资料或用户确认，而非猜测？
9. EDA option 是否保持原始字面名称；是否没有因重构增加、删除或改写原 option 集合？
10. BUILD 场景是否确有必要；producer 工具/版本、基础设计、design ID、输出、所属 case 和生成状态是否可追溯？`build_design.tcl` 是否只造数，不执行被测动作？
11. golden、日志、PASS 文本及 EDA 输出是否来自可信实机基准；是否明确区分文档检查、TCL 语法、结构检查、design 构造和实机运行状态？
12. Excel 行、case 目录、提示词、输入资料、修改记录和验证记录是否一一对应并完成归档，且不含无关秘密？

最终回答中必须报告：`人工语义审查：PASS`，或列出规则序号和缺口；不得用静态 PASS 替代此结论。
